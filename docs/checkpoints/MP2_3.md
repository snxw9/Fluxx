## How it works

### The strip (B1)

- **What:** per video source, one low-resolution picture per 0.1 s slot of SOURCE time: the first picture of the stream whose pts lies in the slot. Long edge 480 px (never upscaled), JPEG q70 (format choice: see B1 below).
- **Scope:** the USED range only: `UsedRange.of(project)` (each visible video layer's in-point to out-point plus the 10 s margin, merged per source, clamped to the source), exactly the PCM cache / peaks / thumbnails rule. Never a whole-source decode.
- **Coverage:** a slot is covered once every picture of it has been decoded (the run started at or before the slot's start, or at the stream's start). Only slots in scope are covered or kept; the pre-roll from the sync frame before the scope decodes but adds nothing.
- **Lookup (`StripIndex.atOrBefore`):** the latest picture at or before the requested source time, provided every slot from it to the target's slot is covered (at most 64 slots back); otherwise a miss (the old path). Before the stream's first picture: that picture (MP2.1's rule). It never returns a later picture, so a backward sweep is monotone by construction.
- **Disk cache:** `cacheDir/mp23-strip/<sha1(uri) 10 bytes>-<size>-<lastModified>-v1.strip` (append-only encoded pictures) and `.sidx` (coverage, first-picture pts, slot -> pts / offset / length; written whole to `.tmp` and renamed, every 32 pictures and at the end of every run). On open, pictures whose bytes are missing are dropped and the data file is cut back to the index. Files of another version are deleted. LRU over 256 MB of ALLOCATED bytes (`st_blocks`), files in use never evicted. Partial coverage survives restarts.
- **In RAM:** the renderer keeps uploaded pictures (RGBA GPU buffers) in a 6 MB LRU (`StripFrames`).

### The builder (B1)

- **One decoder at a time** on one background thread (`fluxx-strip`, `THREAD_PRIORITY_BACKGROUND`): MediaCodec with CPU output (flexible YUV 4:2:0 through `getOutputImage`, P010 read by its high byte, BT.601 / 709 and range from the stream's colour aspects), `KEY_PRIORITY` 1 (best effort). Kept pictures are downscaled (luma: mean of four samples per output pixel) and JPEG-encoded; the others are released unconverted.
- **Order:** sources by their distance from the playhead; within a source, the uncovered part nearest the playhead's source time, 10 s runs, outward (forward first on a tie). A run continues without a seek when the decoder already stands there.
- **When:** planned on the render thread only while the preview is paused (after decode-behind, then every 500 ms while it has work). Runs only while `MediaWork.mayRunBackground()` (not playing, not scrubbing, 300 ms after the last foreground moment) and the renderer has neither rendered nor decoded behind for 300 ms. Paused otherwise; its decoder closes after 3 s paused, when done, on Play (cancelled at the first playing frame), on onTrimMemory, or when its source leaves the project / its run leaves the used range (what is covered stays valid; a longer trim extends coverage later).
- **Memory:** before it starts, the render thread checks the room it needs (`DecoderKeys.decoderBytes` at the source size, as any decoder) against `MAX_DECODERS` (4, or 2 on low RAM), the MP1.2 budget (a fifth of RAM) and the codec's instance count; when it does not fit it records why (`strip-blocked why=cap|budget|instances`) and waits. While building it counts as one decoder with those bytes in `CompositionRenderer.decoder()`'s room loop, and is dropped there first (after the warm decoders, before any pool decoder) when a frame needs the room (`dropForRoom`, waits at most 300 ms for its close).
- **Export:** a renderer without a surface (export, offscreen) has no store, no builder and no strip lookups (`scrubStrip = surface != null`); `StripBuilder(export = true)` and `StripFrames(export = true)` never touch the store (JVM test `exportNeverBuildsOrReadsTheStrip`).

### Showing a strip picture (B2)

- **When:** only while AUD2's policy says scrubbing (`approximateFrames`: a seek within 250 ms of the previous one), only for requests the layer's open decoder could not serve without a seek, and only where the source strip covers the target. Then the layer draws the strip picture at or before the target and its decoder is not touched (no seek per target, no decoder opened). The decoder keeps a request (full size, as before MP2.3) when: moving **forward**, it decodes on to the target within its GOP (`VideoDecoder.scrubWithoutSeek`: ScrubFloor's own forward condition); moving **backward**, its cache proves the frame or it stands at most 200 ms before it (`cheapFor`), because there the bounded decode would walk forward while the finger goes back (the out-of-order frames of the baseline). The direction is each layer's last scrub request. Not covered: the bounded decode as before (`ScrubFloor`); never blocking.
- **The exact frame:** unchanged: the frame is marked approximate, so the preview renders it exactly 120 ms after the last move (AUD2's settle).
- **Feeding:** the existing CPU-bitmap path of image layers: JPEG -> `BitmapFactory` (ARGB_8888) -> `FluxxEngine.bitmapBuffer` (RGBA `AHardwareBuffer`) -> `RenderBridge.layer`. Each layer's strip pictures use their own native layer slot (the layer id with bit 62 flipped), so the video slot keeps its YUV pipeline for the exact frame that follows. Geometry: the source's crop size (as last decoded, else the track size), rotation and pixel aspect, so the picture covers the same quad. **No Vulkan code was changed.**
- **Multiple layers:** each uses its own source's strip; a layer without coverage falls back alone.

### Decode-behind (B2)

- A paused, exact frame idle for 200 ms (`ScrubPolicy.BEHIND_IDLE_MS`): for each decoder the last complete frame used, `VideoDecoder.decodeBehind` checks whether its cache already answers the frame before the playhead (`FrameCache.runBefore` < `DecoderPlan.BEHIND_RUN_BELOW` = 2: consecutive frames of one run, the playhead's own included). If not, it seeks to the sync frame before them (one GOP earlier when the playhead is near its sync frame) and decodes forward up to the playhead, not past it. The frames are the decoder's own output and are served by the cache's exact rule, so pictures are those a straight decode gives (golden test).
- `cacheFrames` is the existing budget (16 MB: 5 frames at 1080p, 4 at 1440p, 6 at small sizes): after decode-behind, 3 to 5 backward steps are cache hits.
- **Why only then:** with the frame before the playhead cached, the first step back is already a hit (after real playback this is the normal case: the cache holds 2-5 frames behind it). Running anyway cost a regression on the device: on MKV sources its sync seek landed a GOP early and a step back that cancelled it half-way found the cache emptied (366-2492 ms, see B3). So decode-behind acts after a jump or seek that left nothing behind the playhead (a pause on a sync frame: the golden test's case).
- Cancelled at once by any request (play, seek, edit: the generation changes); runs on the preview thread, so it never competes with a foreground request; it holds no extra decoder.
- **Warm-up interplay (MP2.1):** the warm planner runs only while playing; decode-behind and the builder only while paused (the builder is also gated by MediaWork). A Play press cancels decode-behind (generation) and the builder (first playing frame).

**What the baseline shows (b0r4, AUD2's scrub policy and MP1's `ScrubFloor`):**
- **Fast backward sweeps starve.** Each 16 ms seek cancels a render that needs a seek and a GOP decode, so few frames finish: at 8x, 1 to 27 frames in 3 s (H.264 typical 2, VP9 worst 1, AV1 1080p 19). The first frame of a backward 8x sweep came 240 ms to 2.1 s after the first move, on every file.
- **Even slow backward scrubbing is out of order on long GOPs.** At one frame per 100 ms every request is a scrub request; the bounded decode (4 frames) then walks FORWARD from the sync frame while the finger walks back: 23 of 28 frames out of order on the typical H.264 clip, 20 of 28 on VP9 worst, 15 of 24 on AV1 1080p, with the shown frame up to 2.6-8.7 s behind the target. (The brief expected this control to be fine; it is not, on long GOPs.)
- **Never ahead:** 0 frames later than the target in every case (MP1's floor rule holds).
- **Forward sweeps are fine** at 1x and 2x (the decoder decodes on), but fall behind at 4x / 8x (lag up to 2.3 s, few frames).
- **The first backward step after a pause** (one frame back, the decoder idle after real playback) is already a cache hit on every codec: **12-35 ms**. The 229-267 ms of AUD2 is the first frame of a backward *sweep* (several frames back: a seek), which is what the strip addresses.

### Strip cost (what the builder really wrote and spent)

Bytes are the files on the phone (`mp2_3/strip_cache_ls.txt`, allocated); build time is the builder's active decode + convert + encode time from its `strip-stop` probe in the first after run (`b3`, background priority, preview idle), per minute of source decoded.

| File | Used range | Strip on disk | MB per minute of source | Build time per minute of source |
|---|---|---|---|---|
| H.264 1080p30 (typical) | 60 s | 6.9 MB | **6.9** | 16.3 s (598 frames in 5.4 s) |
| H.264 1080p24 (Seal) | 60 s | 6.6 MB | **6.6** | 14.3 s (1438 frames in 14.3 s) |
| VP9 1920x1440 (worst case) | 122.8 s | 19.3 MB | **9.4** | 15.3 s (1899 frames in 24.1 s) |
| VP9 1080p (Seal) | 60 s | 3.8 MB | **3.8** | 12.8 s (1439 frames in 13.3 s) |
| HEVC, 50-minute file (clip 20:00-21:00) | 19:50-21:10 (80 s) of 3018 s | 15.0 MB | **11.3** | ~13 s (wall; its stop probe was not captured) |
| HEVC 1440x1080 (Seal) | 15.3 s | 4.1 MB | **16.2** | 20.5 s (459 frames in 5.2 s) |
| AV1 640x480 (Seal) | 11.8 s | 1.4 MB | **6.9** | 17.8 s (352 frames in 3.5 s) |
| AV1 1080p (Seal) | 137.7 s | 20.7 MB | **9.0** | 19.3 s (4127 frames in 44.3 s) |

- **3.8 to 16.2 MB per minute of source** (all under the 20 MB/min design bound); **13 to 21 s of background work per minute of source** (the decode dominates: the builder decodes every frame and converts one per 0.1 s).
- **Only the used range:** on the 50-minute file the strip holds 19:50-21:10 (80 s of 50 min, 15 MB); the builder's seeks and decodes stay within the range's sync frame and the range's end (JVM test `theBuilderStaysInsideTheUsedRangeOfALongSource`, and the device coverage probe).
- **Share of sweep targets served from the strip** (frames shown while moving): 86-100 % on backward sweeps and back-and-forth; 0 % on forward sweeps at 1x-4x on 30 fps sources (the decoder keeps up and serves them at full size), 96-100 % at 8x. Where the strip did not cover (not measured here: the strip was always complete), the old bounded decode serves the target.
- **Disk cache on the phone:** 76 MB allocated mid-session (9 strips: the 8 files plus the typical clip under a second URI spelling, `file://`, used by `Mp21Test`; strips are keyed by the URI string); **43 MB at the end** (`mp2_3/strip_cache_ls_end.txt`). The difference is Android's own cache trimming: /data was 92 % full (8.5 GB free) and each `adb install` asks the system to free space, which removes app cache files oldest-modified first. It removed whole older strips and the index files of others (index files are rewritten only while building, data files are touched on every open). `StripFile` handles both cases: a missing or foreign index rebuilds from nothing, pictures whose bytes are gone are dropped with their coverage. In the final run three partly removed strips were rebuilt before the sweeps (HEVC 1440x1080 51 % -> 100 % in 3.1 s, AV1 640x480 87 % in 0.5 s, AV1 1080p 6.8 % in 38.8 s: 4127 frames in 41.5 s active).
- **Cache budget:** 256 MB of allocated bytes (LRU, files in use kept); it was never reached in this session (no eviction by the strip cache itself).
- **In RAM:** at most 6 MB of uploaded pictures (a 480x270 RGBA picture is ~0.5 MB: ~11 pictures), dropped on onTrimMemory; the index of a source is a few arrays (about 21 bytes per 0.1 s slot of the source: ~0.6 MB for the 50-minute file).
- **Persistence:** strips built in one run were reused by the next runs (and by the next process): every after run found the strips complete at its first check.

## Contracts

- **Unchanged:** the gesture protocol, `EditorAction` (no new action), the batch / draw contract, the evaluator, `SetKeyEasing`, preparation, the document schema (v13), the project model, the timeline scroll model, audio, `CompositionExporter`.
- **No Vulkan code changed:** strip pictures go through `FluxxEngine.bitmapBuffer` and `RenderBridge.layer` (existing JNI) on their own layer slot. Not touched: the draw path, per-layer `flush()`, VkImage import / sampler, the pipeline cache, frame pacing, culling logic.
- **Cache / renderer state only:** the strip is a cache in `cacheDir` (never in the document or undo); each layer's scrub direction is renderer state.
- **`PreviewController`:** public API unchanged; internally decode-behind after 200 ms idle, and builder ticks every 500 ms while paused with builder work. **`CompositionRenderer`:** new optional `scrubStrip` constructor parameter (default `surface != null`), `decodeBehind`, `stripTick`.
- **Memory limits:** MP1.2's budget, `MAX_DECODERS` and the onTrimMemory release stay in force; the builder's decoder counts against all three and is dropped first.
- `mp23` was merged into `master` on 2026-11-28 at `4582f61` (see `MP2_2.md`, Part A).

## Not verified

- Real finger scrubbing (seeks were scripted at the UI frame rate through the preview path, not touch input), and the look of the 480 px strip pictures by eye.
- Saver ON and on battery (every comparable run was Saver 0 on AC); other devices; thermal behaviour over long sessions.
- A sweep over a range the strip does not cover, as its own device case (the miss path is the unchanged bounded decode; the lookup rule is JVM-tested).
- Sources with much more than an hour of used range (the 50-minute file had an 80 s range); codecs not in the matrix; 10-bit HDR sources (P010 is read by its high byte, no tone mapping).
- Showing a strip picture costs 15.5-15.8 ms p50 on the render thread from disk (read, JPEG decode, a new GPU buffer each time; 0.07 ms from RAM), which caps sweeps at ~30-35 shown frames per second. Not optimised (a buffer pool would need a JNI change).
- After real playback decode-behind almost never runs (the cache already holds the frames behind the playhead); its effect was measured in the golden test only.
