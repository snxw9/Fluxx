## B1. The warm planner (`UpcomingUse`, pure)

`app/src/main/kotlin/com/fluxx/android/render/UpcomingUse.kt`.

**Input:**
- the visible video clips: start, end, in-point, source, decoder class (codec + size) and decoder bytes;
- the frame time and whether it is playing;
- the culled layers' return times, read from the renderer's own culling test;
- the clips not visible at their own start;
- the open decoders: key, source, bytes, and whether the current frame uses them;
- the warm-ups in progress;
- the MP1.2 budget, the cap and the measured costs.

**Output:** the warm-ups due (soonest first), the blocked ones (budget or cap), the set of wanted warm-ups, and the sources to keep from the hidden release.

| Rule | Implementation |
|---|---|
| Only while playing | `enabled(export, playing) = !export && playing`. Paused or scrubbing: `Plan.NONE` (nothing due, nothing wanted) |
| Horizon | `max(0.5 s, 2 × measured open + seek + first frame)`, capped at 2.5 s, per decoder class; 1.5 s until the class is measured |
| Cut | A clip starting in (now, now + horizon], visible at its start, gets a warm-up unless it continues an open decoder. "Continues" means a clip of the same source, active now, that will stand at most 100 ms before the new in-point (it decodes on) or within `DecoderKeys.SHARE_US` of it (the decoder is shared). Target: the in-point. Deadline: the clip start |
| Re-entry | A cold-culled layer that the culling test says is visible again at time r. The renderer already starts decoding it (undrawn) 0.5 s before r (MP1's look-ahead), so the deadline is d = r − 0.5 s and the target is its source time at d. An open decoder of the same source that the current frame does not use is re-positioned (no second open, no new memory). The source is kept from the 3 s hidden release while it is due back within the horizon |
| Budget / cap | A warm-up must fit `DecoderKeys.decoderBytes` within the budget (a fifth of RAM) AND within `MAX_DECODERS` (2 on low-RAM devices). Every open decoder counts, the current frame's included, and so does every warm-up in progress. Otherwise the warm-up is BLOCKED (counted and logged); nothing is evicted to make room for it |
| Order | Soonest deadline first, then layer id; the pool runs one at a time |
| Source time | `sourceIn + (t − start)`: the model has no speed, stretch or remap. A JVM test checks it against `FramePlan.forEachActive` |

JVM `UpcomingUseTest` (13 tests) covers:
- horizon maths, including per-class horizons;
- a contiguous continuation needs no warm-up (nor does a small forward gap or a shared time);
- a non-contiguous cut warms at its trimmed in-point;
- the source mapping equals FramePlan's;
- a clip starting exactly at the horizon is due; 1 µs later is not, and one already started is not;
- budget refusal (warm-ups count against it);
- cap refusal (current frame plus warming; low-RAM cap of 2);
- paused or scrubbing: nothing is wanted;
- export never plans;
- several due: soonest first, and a warm-up already running is not restarted;
- a clip hidden at its start gets no warm-up;
- re-entry deadline, target, decoder reuse and keep; also beyond the horizon, after release, and with a busy decoder;
- a return after the clip ends gets no warm-up.

## B2. Integration (`WarmPool`, renderer)

- **`WarmPool`** (`render/WarmPool.kt`, JVM-tested with fake decoders) holds warm-ups by layer. The renderer calls `frame()` once per preview frame:
  - the planner runs (preview playback only);
  - each blocked warm-up is counted once;
  - unwanted warm decoders get the 3 s `DelayedRelease`;
  - when nothing is running, the first due warm-up starts on the `fluxx-warm` thread at background priority (`MediaWork.background`).

  A warm-up opens a decoder (or takes the pooled one to re-use), calls `frameAt(target)`, then holds the decoder. `frameAt` follows the existing seek rules: `DecoderPlan.decide`, the sync frame, and decoding up to the frame after the target, so the cache proves the target's frame.
- **Gate:** between decode steps the work calls `MediaWorkPolicy.warmMayRun(currentFrameLate, untilDeadline)`. It waits while the current frame has run longer than one frame interval, unless its own deadline is within 300 ms.
- **Handoff** (`CompositionRenderer.handoff`, just before the layer's decoder is fetched):
  - If the decoder under the layer's key can serve the request cheaply (`VideoDecoder.cheapFor`: a cache-proved frame, or at most 200 ms of forward decode), it keeps the layer and the warm decoder is dropped at once.
  - Otherwise the warm decoder takes the key and the stale one closes.
  - A frame that needs a warm-up still running waits for it, up to 1.5 s, with the warm thread raised to display priority.
  - The first frame of the new clip is the cached one.
- **Interplay with MP1.2:**
  - `DecoderRetention` is unchanged. Warm decoders are not in the pool, so they are never "idle".
  - The 3 s hidden release keeps any source in the plan's `keepUris`.
  - `decoder()` counts warm decoders against the cap and the budget and drops them first: the current frame always wins, and a decoder the current frame uses is never evicted.
  - onTrimMemory releases at once every warm decoder the plan does not want.
  - A paused preview wakes every 500 ms while a warm decoder is held, so the 3 s release still happens without a new frame.
- **Costs:** every warm-up's open + seek + first frame, and every decoder a frame opened itself, feeds an exponential average per decoder class. Nothing is persisted.
- **Export:** `CompositionRenderer(..., warmUp = surface != null)`, so the exporter's offscreen renderer has no pool. `WarmPoolTest.exportNeverConsultsThePlanner` asserts that the planner is never called in export mode.
- **Probes** (test-only, null in the app):
  - `MediaProbes` lines: `warm-start`, `warm-ready`, `warm-used`, `warm-release`, `warm-blocked`, `warm-wait`;
  - `VideoDecoder` open lines carry `openus=`, frame lines carry `seekus=`;
  - `PreviewFrames.testRender` reports render calls by reason.
- **JVM `WarmPoolTest`** (8 tests) covers:
  - export never consults the planner;
  - open, position and take at the cut;
  - a stale warm decoder is released;
  - when paused, a warm decoder goes after 3 s, and at once on trim;
  - `dropForRoom` takes unwanted decoders first, then the one due last;
  - a frame waits for a running warm-up;
  - a cancelled running warm-up closes itself;
  - re-entry re-uses the pooled decoder.
- **Found on the A16 (fix `33c790a`):**
  - **The case:** a cut at in-point 0 of a file whose first picture comes after 0. This covers several Seal VP9 files and Project 1 clips 17 and 20–28; MP1.2 had noted clip 17's first frame at 0.105 s.
  - **What went wrong:** the cut asks the decoder for a time before any picture. `cheapFor` said no, so the warm decoder was released as stale; even a normal decoder re-seeked on that request.
  - **The fix:** `VideoDecoder` now remembers the stream's first picture when a run starts at the stream start, and answers any earlier request with it. That is exactly what a straight decode returns under the nearest-frame rule, so pixels are unchanged (see the golden test and the export digests below).
  - **Seal sequence:** before the fix 7/9 cuts under 100 ms, with 2 warm-ups released as stale; after it 9/9, all warm-ups used.
- **Golden test (`Mp21GoldenTest`):** 12 cuts (4 of them to VP9) plus one re-entry, rendered offscreen with warm-up ON (playing) and OFF.
  - **360 frames compared, 0 differ.**
  - Warm-ups started 12, used 12; released unused 0; failed 0; frame waits 0.
  - Blocked: 1 (3 in the run before the fix).

## B3. Playback position out of editor state

**The cause had two parts:**
1. `EditorViewModel.reportPosition` replaced the whole snapshot `state` on every presented frame, so everything that read the editor state recomposed.
2. `EditorScreen` collected the whole `PreviewState`, whose `positionUs` changes every frame, so even reading `.playing` recomposed the screen.

**How it works now:**
- `EditorViewModel.playbackPosition` is a UI-only `State<Long>`: never in undo history, never saved. While the preview plays (`playbackRunning`, set by `EditorScreen` from its controller), position reports go there.
- `EditorViewModel.state` returns the stored state with the live playhead, read *without* snapshot observation. Event handlers see the true position, but compositions are not invalidated every frame.
- The first report after playback stops (the pause frame, or the end) is a `Seek`, exactly as before, so the editor state is correct whenever playback is not running.
- `EditorScreen` now collects only `playing` and `message` from `PreviewState`.
- `EditorAction`, the reducer, undo and the document are unchanged.

| Consumer | Before (while playing) | After |
|---|---|---|
| EditorScreen (whole screen) | recomposed every frame | not every frame |
| Timeline view | recomposed every frame (playheadUs param) | 1 composition in 5 s |
| Clip rows | recomposed with the view (11 rows × every frame) | 33 in 5 s (as the layout window changes) |
| Timeline follow (scroll) | `LaunchedEffect(playheadUs)` per report | a `withFrameNanos` loop on the heard clock (same rule, `TimelineFollow`) |
| Ruler | draw phase, from the scroll state | unchanged |
| Playhead pill: timecode readout, marker tint | inside the view's recomposition | its own scope reads `playbackPosition`: 135–143 recompositions in 5 s (its text changes every frame) |
| Twirl rows: key highlight at the playhead | draw-phase reader of the param | draw-phase reader of the live position |
| Twirl add-key button state | updated every frame | frozen at the last composition while playing; the add itself uses the live time. Left as is: recomputing it every frame would recompose the side controls |
| Marker tap / hold at the playhead | composition value | live at the tap |
| Markers prev / next, undo / redo, split, flip, paste, add at the playhead, pause floor | composition-captured playhead | live at the event (a read-at-use delegate in EditorScreen plus the state getter) |
| Preview selection box | updated every frame | Canvas draw-phase read of the live position |
| Preview tap-to-select and text hit test | every-frame value | live at the tap |
| Preview text overlays (selection, box-width handle, text metrics of the selected text layer) | updated every frame | last composition while playing. Left as is: text editing pauses playback |
| Inspector: values, Graph page, Graph time tile, key readouts, ClipQuickActionBar | updated every frame (whole screen) | the sheet's scope reads the live position while playing with the sheet open, and recomposes only then (its values change) |
| EditorActionBar (play / pause) | every frame | only on play / pause |

## Contracts

- **Unchanged:** the gesture protocol, `EditorAction` (no new action), the batch/draw contract, the evaluator, `SetKeyEasing`, preparation, and schema v13.
- **UI state only:** selection, expansion, scroll and zoom, and the new playback position.
- **`PreviewController`:** the public API is unchanged. Internally it gained a test-only render-reason probe and a 500 ms wake while paused with a warm decoder held.
- **`CompositionRenderer`:** gained an optional `warmUp` constructor parameter, defaulting to `surface != null`.
- **Not touched:** the Vulkan draw path, per-layer `flush()`, VkImage import, the pipeline cache, frame pacing, culling logic (its visibility test is only read ahead), `CompositionExporter`, audio, the scroll model and the project model.
- **Memory limits:** MP1.2's budget, `MAX_DECODERS` (4, or 2 on low RAM) and the onTrimMemory release stay in force, and warm-ups count against all of them.
