## B2. Safety audit: everything that can close, recycle, overwrite or release an image or buffer, or destroy a GPU object

**What "safe" means here.** The render path stages at most 4 draws (`mDrawOrder`) and records them only when it submits; every submit (`submitWork`) waits on its fence before returning. So between submits no GPU work is in flight. A staged draw holds two things: a native `AHardwareBuffer` reference (`AHardwareBuffer_acquire`, `vulkan_renderer.cpp:1457`), which keeps the memory alive; and the slot's `VkImage`, view, descriptor and pipeline, which must not be destroyed before the submit. The native reference does **not** stop a live producer writing into the buffer. A decoder's `ImageReader` hands a closed `Image`'s buffer back to the codec, and the codec writes the next picture into it. So the real hazard is a closed codec image of a decoder that is still decoding.

"Narrowed" in the last column means: the flush before `frameAt` runs only when the decoder about to be advanced already has an image staged in the current batch (the shared-decoder case). Every other flush stays.

### Image layout transitions, external queue ownership and producer fences (today)
- **Layout.** One barrier per newly imported image, recorded in the batch before its render pass: `UNDEFINED -> SHADER_READ_ONLY_OPTIMAL`, `srcStage TOP_OF_PIPE`, `srcAccess 0`, `dstStage FRAGMENT_SHADER`, `dstAccess SHADER_READ` (`vulkan_renderer.cpp:1554-1582`; `transitioned` is reset on every import, `:1458`). No transition back. With `oldLayout = UNDEFINED`, the spec allows the implementation to discard the image contents.
- **Queue ownership.** None. `srcQueueFamilyIndex` / `dstQueueFamilyIndex` are `VK_QUEUE_FAMILY_IGNORED` (`:1563-1564`). For memory imported from an `AHardwareBuffer`, the spec's way to get defined contents is an acquire from `VK_QUEUE_FAMILY_FOREIGN_EXT` (or `EXTERNAL`) with the producer's layout. It works on this Mali driver (the golden and identity tests are byte-identical), but the spec does not guarantee it.
- **Producer fences.** None. The `Image`'s acquire fence (`Image.getFence()`, API 33+) is never read, and the `AHardwareBuffer`'s fence is not imported as a semaphore or waited on. The code relies on `MediaCodec` -> `ImageReader` (`ImageFormat.PRIVATE`) handing over a finished buffer by the time `acquireNextImage` returns. **Not verified** on the A16; a decoder that signals late would show as torn or stale pictures, not as a crash.
- **Present and readback** are correctly ordered: the present blit waits on the swapchain semaphore, `render()` waits `mInFlightFence` before reusing its command buffer, and the next batch's render pass depends on the blit's TRANSFER read (subpass dependency 0, `:1254-1268`).

## B3. Measurements on the A16

### Setup
- **Measure class:** `Mp22RenderTest` (`app/src/androidTestMedia`).
- **Source:** the typical H.264 file `a-X8h8cgzOI` (1920x1080, 30 fps, 60 s). It is read in place through its MediaStore content URI, found by `DISPLAY_NAME`.
- **Composition:** 1920x1080 @ 30 fps; preview resolution FULL. N layers are tiled.
- **Distinct decoders:** in-points 2 s + k x 7 s.
- **Shared decoder:** every layer at 10 s.
- **Preview:**
  - one long-lived surface renderer (as the app keeps one), on a SurfaceView, with `playing = true`;
  - frames rendered back to back: 30 warm-up frames, then 150 measured; a 3.5 s settle before each case;
  - the cap (4) and memory budget unchanged.
- **Export:** the real `CompositionExporter` (its own renderer, readback, H.264 encoder):
  - 30 frames per case; 15 at distinct N=6/8, where decoder rotation makes frames 0.7-2 s each;
  - the first frame (a fresh session: device, pipeline, decoder open) is reported separately.
- **Raw data:** every per-frame sample is buffered and reported after its case. Per-frame rows are the `MP22RAW` lines in the `.raw` files.
- **Runs, planned twice (not re-runs):**
  - preview: run 1 `b3r1-Mp22RenderTest` at 38.1-38.2 °C; run 2 `b3r2-Mp22RenderTest-preview` at 38.7-38.9 °C;
  - export: run 1 `b3r1x-Mp22RenderTest-export` at 38.8-38.9 °C; run 2 `b3r2x-Mp22RenderTest-export` at 38.7 °C;
  - all on AC with Battery Saver off (`TestDeviceState` in each `.txt`).
- **Which timings overlap:**
  - `total` (preview: `STAGE_FRAME`; export: the `render()` call) contains everything below except, in export, readback / YUV / encode wait.
  - `decode` = time inside `frameAt`.
  - `import` = native `setFrameLayer` import, `pipeline` included.
  - `record`, `submit` (the `vkQueueSubmit` call) and `fence` (CPU wait for the batch fence) are sums over all batches of the frame. They sit inside `flushes` (mid-frame flushes, Kotlin wall) plus `finish` (last batch + present CPU).
  - `gpu` = GPU timestamps of the batches. It overlaps `fence` (the CPU waits while the GPU runs), so fence >= GPU.
  - `present` = present fence wait + acquire + record + `vkQueuePresent` (CPU, inside `finish`).
  - Export: `readback` = copy to the host buffer (submit + wait); `yuv` = CPU RGBA-to-YUV conversion; `encodeWait` = encoder input wait + output drain. All three are outside `total`.

**What the counts show:**
- **Every video layer imports every frame** (imports = drawn layers). The exceptions are frames where the decoder held its picture (`sameBuffer`).
- **Submits = render passes = N** (1 + the per-video flushes) for N drawn video layers.
- **Above 4 drawn layers, every slot is evicted and rebuilt every frame:** shared N=6 / 8 show 6 / 8 pipeline creations, YCbCr conversions and slot evictions per frame, in preview and in export. Measured cost 2.8-6.4 ms per frame (the `pipeline` column).
- **A per-buffer import cache would need about 19 entries per 1080p H.264 decoder** (each decoder cycles through ~19 distinct `AHardwareBuffer`s), and 31 for the 1440p VP9 file. Steady-state hit rates in preview: 87% (typical H.264, distinct), 94-98% (shared), 69% (VP9).
  - An LRU of 4-16 entries per renderer hits 0% with distinct decoders, because their buffers interleave. With shared decoders the 4-entry hits are only the same buffer drawn by several layers in one frame.
  - Export runs are only 30 frames, so the cache would still be warming: 34-92%.

**What changed:**
- `StagedDecoders` (new, pure; `StagedDecodersTest`, 9 JVM tests) records the decoder keys with an image staged since the last flush.

- The set is cleared with `staged` on every flush, at `begin`, at `finish`, and after a cancelled or failed frame (`renderTarget`'s `finally`). A cancelled frame's draws are therefore no longer submitted by the next frame's `releaseHidden`.

**Test-only switches (default off):**
- `testFlushAlways` restores the old rule. It replaces the removed `testSkipVideoFlush`.

## B2. Export readback memory

## B3. Saved pipeline cache and warm-up
**What changed:**
- **Load:** `cacheDir/vk_pipeline_cache.bin` at every session's creation (preview and export share it). The header is checked: size, version, vendor, device, `pipelineCacheUUID`. A missing, stale or corrupt file, or one over 4 MB, means an empty cache. If the driver rejects the data, creation is retried empty. Init never fails because of the file.
- **Save:** `vkGetPipelineCacheData`, only when pipelines were created since the last save. It runs:
  - at session teardown (backgrounding destroys the preview surface, which stops the preview and tears the session down);
  - when the paused preview is idle (`PreviewController`, after decode-behind; never while playing).
  - Written to a per-session temp file, `fsync`, then `rename`.
- **Warm-up:** at session creation, the RGBA slot pipeline (images, solids, strip pictures) is built and dropped.
  - **Video pipelines are not warmed:** they need the external YCbCr format of the first decoded buffer, and no format registry was built.
  - The saved file covers video pipelines once they have been seen.
- **Threads:** all Vulkan calls stay on the session's owner thread.
- **Test-only:** `RenderBridge.testIgnoreSavedPipelineCache` (load nothing, still save); `pipelineCacheInfo`.
- **File size: 4850 bytes** (cap 4 MB).

## B2 safety table rechecked
Only rows 1 and 13 change. Every other row's protection is unchanged.
- **The staged set:**
  - `StagedDecoders` is per renderer and used only on that renderer's owner thread: `FluxxPreview` for the preview, the export worker for export.
  - It is filled when a video image is staged (`CompositionRenderer.kt:1069`).
  - It is cleared together with `staged` in `flush()` (`:619`), at `begin` (`:877`), at `finish` (`:1088`, `:468` in the prepared-text path) and after a cancelled or failed frame (`:843`).
- **Row 1, shared decoder advanced in one batch:** now protected by the narrowed rule (`:1050`): a flush runs exactly when the key has an image staged.
  - This covers warm-culled layers: their `frameAt` runs the same check, and they stage nothing.
  - Two kinds of evidence:
    - The test-only check (`VideoDecoder.testAdvance` on every decode, seek and close, on every thread: render, warm, strip, decode-behind) saw **0 violations** in `Mp22GoldenTest`. That covers 108 frames, shared and distinct, preview with the look-ahead decode, export, a backward seek within `SHARE_US`, and VP9 with its 3-frame cache.
    - The output was byte-identical to flush-always.
- **Rows 2-6 and 15 (eviction, hand-off, pool re-use, retention / delayed release, raster eviction, close):** each still runs its own `flush()` before closing. That flush also clears the staged set (`:158`, `:206`, `:287`, `:294`, `:631`, `:760`).
- **Rows 7-10 (strip pictures, decode-behind, strip builder, `onTrimMemory`):** unchanged. Decode-behind runs between frames, when the set is empty.
- **Rows 11-12 (native slot eviction / import):** unchanged. Every submit still waits on its fence; B1 changes only when Kotlin flushes.
- **Row 13, cancelled or failed frame:** **changed and safer.** `staged` and the set are now reset when a frame does not complete. The next frame's `releaseHidden` therefore no longer submits the stale draws (wasted work before), and the next `begin` drops them natively. Golden: a frame cancelled after 2 staged video layers, then the next frame, is byte-identical to a clean render (preview and export).
- **B3 threading:** `savePipelineCache` runs on the owner thread only: `PreviewController`'s render loop when paused, and session teardown (`cleanup` after `vkDeviceWaitIdle`). The file path is process-wide, under a mutex. Writes go to a per-session temp file, then `rename`.
- **B2:** the readback still runs on the owner thread after its fence. The invalidate sits between the fence wait and every CPU read.

## Phone checklist for Snxw
1. **Multi-layer playback:** play a project with 3-4 video layers from different clips (or Project 1). Smooth, no flicker or wrong frames.
2. **Two copies of one clip slightly offset:** duplicate a clip onto a second layer, shifted 1-2 frames. Play, pause, step back and forth. Both layers show their own frame; no tearing or swapped frames.
3. **Scrubbing:** scrub back and forth fast over multi-layer video, then release. The exact frame settles.
4. **A cut:** play across a cut between two clips. No freeze longer than before.
5. **Export timed by hand:** export a 30-60 s project and time it; it should be clearly faster than before (about half the time for simple projects). Check the exported video looks right.
6. **Restart the app:** close Fluxx fully and reopen a project. The first frame should appear at least as fast as before. Pause in the editor for a second (this saves the pipeline cache), close, reopen.
