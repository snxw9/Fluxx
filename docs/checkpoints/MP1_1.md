# MP1.1: crashes on big imports, bulk-add icons, test-state logging

Branch `aud1`, continued from `671e2f9`. Not merged. Device: A16 (SM-A165F, Android 16, 4 GB, density 2.8125, 1080 px wide). The app Snxw tests is the debug package `com.fluxx.android.debug`.

**Result in one line:** all three crashes have one root cause. The timeline asked Compose for a node wider than it can lay out. It is not an MP1 regression (the AUD2 tip crashes the same way). Fixed by a zoom ceiling tied to the composition length. Bulk add is now one edit, with Sequence and Stagger icons.

## Part B: the fix (`dfcf3b5`)
- **What:** `TimelineZoom.ceiling / floor / clamp`. The zoom used is the chosen one within a ceiling that keeps the content within **200,000 px**:
  - computed for the composition's span: the longer of its length and the latest layer end, because every clip box is sized by its own duration, so a clip longer than a fixed-length composition is covered too;
  - at the real density;
  - with the window width bounding the half-viewport spacers.
- The floor drops below 0.5 dp/s only past about 39 h.
- Pinch scales from the zoom in use, so there is no dead zone after the composition grows, and its handler reads these inputs fresh.
- Every node sized by duration (clip boxes, thumbnail strips, waveform / twirl rows, the ruler) is bounded by that content width.
- **Not virtualised** (the prompt's acceptable minimum). The scroll model under clip and key drags, edge auto-scroll, snapping and the ruler is unchanged, because those must behave exactly as before and cannot be finger-tested here.
- **What zoom is lost** (A16, 2.8125x, 1080 px):

| Composition | Highest zoom | px per frame at 30 fps |
|---|---|---|
| ≤ 1 min | 2400 dp/s (unchanged) | 225 |
| 5 min | 236 dp/s | 22 |
| 10 min | 118 dp/s (the default 120 just capped) | 11 |
| 30 min | 39 dp/s | 3.7 |
| 50 min | 23 dp/s | 2.2 |
| 3 h | 6.6 dp/s | 0.6 |

  Frame-level zoom (about 8 px per frame or more) remains up to about **14 minutes** of composition. Beyond that, frames are below a few pixels: frame snapping still works numerically, but single frames cannot be seen or hit. Virtualising the horizontal content would remove this limit (a later pass).

## Part C: bulk add as one edit; Sequence and Stagger icons (`a59eed4`)
- **One `Batch`, one undo:**
  - `BulkAdd` (pure, JVM tested) adds every clip at the playhead (snapped), stacked above the existing layers in selection order;
  - then it applies the layer bar's own `MultiLayerEdits.sequence` / `stagger` with their defaults (gap 0, Reverse off; 2 frames, Reverse on), computed on the state after the adds.
  - `EditorViewModel.addMediaBatch` resolves the picked media off the main thread, in selection order, then dispatches once; one preview update.
  - Nothing is added if an item fails to resolve (before, a failure left the earlier items added).
- **The bar:**
  - Add keeps its icon, its menu and its behaviour.
  - **Sequence** and **Stagger** sit next to it, with the layer bar's monochrome vectors (`InspectorIcons` SEQUENCE / STAGGER). They are enabled for two or more clips and have no text labels.
  - The title is limited to one line so the bar fits on the A16 at the default font scale (layout not measured; see Not verified).
  - A single item still takes the existing single-item flow.
- **Selection order:** the picker already tracks it (an insertion-ordered map). It is used as is.
- **Content-URI test (`c1BulkActions`, 3 and 30 clips):**
  - Add: all at the 2 s playhead. Sequence: end to end from it. Stagger: 2 frames apart, the last selected at the playhead (Reverse on).
  - **Each is one undo step** (undo leaves 0 of the new layers) and nothing crashes.
  - Returned in 200–279 ms for 3 clips and 2.0–2.1 s for 30.
- **Add latency on the main thread:** the add's own main-thread work (`BulkAdd` + the one dispatch) is **89 ms** for 30 clips, the only app message over 50 ms (Looper message timing). The rest of the 2.0–2.4 s is media resolution off the main thread. The two ~1.08 s "frames" FrameMetrics reported came from the test's own `runOnIdle` (Espresso's idle loop runs other main-thread work inside one message), not from the app.

## Part D: test-state logging (`f34c762`)
- **`TestDeviceState`:** every media class records at its start Battery Saver (`low_power`), plugged state, level, temperature, screen and keyguard (status key STATE). A class on battery or with Battery Saver on is marked NOT COMPARABLE.
- **The session runner** records the same per class, skips when the screen is off, waits when the battery is above 42 C, and applies a wall-clock limit per class.
- **Session start / end:** `low_power`, `stay_on_while_plugged_in` and `screen_off_timeout` were recorded and restored.

## Deviations
- **Not virtualised:** the zoom clamp, the prompt's acceptable minimum. Frame-level zoom is lost past about 14 min (table in B).
- **Scenarios run one method per invocation,** because a crash ends the instrumentation.
- **Re-runs, and why:**
  - the first round failed in the test itself (my state helper's format string): all five, fixed, re-run;
  - one Gradle start collided with the concurrent AUD2-tip build (an infrastructure failure) and was retried after it;
  - `s4` after the fix failed once on the test's Compose idle wait during playback; the play step now starts and stops on the main thread without waiting for idle, and the re-run passed;
  - one diagnostic run of `s2a` added main-thread message timing.
- **Bulk add is atomic now:** a failing item adds nothing; before, the earlier items stayed.
- **The single-item path is unchanged:** the detail view's add and relink.
